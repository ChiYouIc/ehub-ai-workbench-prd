# 01 产品概述 — 销售转化画像模块

> 模块：customer-profile-sales（销售转化画像） ｜ 关联 PRD 母本：`plans/customer-profile/customer-profile-sales-prd.md`（v1.1 已定版） ｜ 状态：随定版生效
>
> 决策溯源：Q1–Q28（含 r2 修订），详见 `plans/customer-profile/customer-profile-sales-interview.md`。术语以 `GLOSSARY.md` 客户画像领域一节为准。
>
> 姊妹模块：customer-profile（ops 运营画像，`../ops/`）——同一批客户两套画像，独立生成、独立存储、独立演进（Q23）；本模块复用其已验证模式（调度抢占/整包存储/强校验/审计纪律），差异点见各文档标注。

## 1. 背景与问题

销售团队面对大量活跃客户，缺乏系统化的转化认知：

- 不知道哪个客户质量高、意向强弱、该优先跟进谁——客户筛选完全靠销售个人经验，标准不统一
- 跟进前缺乏快速认知手段，每个客户都要从头研究
- 话术准备靠销售自己写，质量参差且耗时

目标：为每个活跃客户生成一张**结构化画像卡片**（评分 / 速读 / 转化策略 / 可复制话术），帮助销售快速了解客户并决定下一步行动。

## 2. 产品方案

在 `ehub-ai-workbench` 服务中新增**独立模块 `customer-profile-sales`**（Q8）：

- **分析对象（Q1/Q5）**：平台注册、已绑定店铺、**近 7 天存在消费记录**的客户——即运营画像对象的活跃子集（包含关系，Q23）。注意不是"注册线索"，绑定与消费是入池硬条件
- **数据获取（Q2/Q17）**：下游 MCP 服务**已有**，新增 3 个数据工具随本需求同步开发（CRM 基础信息+填报 / 行为日志 / 活跃消费客户清单）
- **分析编排（Q16）**：百炼 Agent 侧配置销售画像技能；skill 全文以本仓库镜像 `designs/customer-profile/sales/sales-skill.md` 为单一事实源，PR review 后手动同步百炼（照搬 ops 模式）
- **评分分工（Q13）**：`leadQuality` / `intentHeat` / `followPriority` 三项 AI 综合判断；`infoCompleteness` **本服务规则计算**（字段非空加权，恒定可解释），不入 AI 输出
- **双触发（Q5/Q12）**：定时扫描每 7 天一轮（扫近 7 天有消费客户）；手动触发任意绑定客户（不限活跃集，休眠客户是销售盘活对象）
- **失败语义（Q4）**：固定 schema 强校验，失败重试 1 次（Q22），再失败即弃并记失败状态，**严禁宽松落库**——无 FALLBACK 降级落库形态
- **存储（Q21）**：独立表 `ai_customer_profile_sales`，v1 覆盖式只留最新；`profile_json` 整包 + 四检索投影列（Q7/Q24）
- **前端（Q10，r2/Q28）**：v1 含前端页面（列表+详情）但**不挂钩 ehub-web**——页面由宿主业务系统（CRM 前端）承载；本模块交付物 = 接口契约 + 画像卡片信息架构 + 设计草图规范

## 3. 目标用户与角色

| 角色 | 说明 | 关注点 |
|---|---|---|
| 销售人员 | 内部登录用户（持有效 JWT），经宿主业务系统前端使用 | 画像查询、评分筛选定位跟进对象、手动刷新、复制话术 |
| 系统管理者 | 内部登录用户 | token 成本归因、分析失败率 |
| 平台调度 | 本服务定时扫描（无人参与） | 活跃集发现、触发分析、多实例互斥 |
| 宿主业务系统 | 前端页面承载方（CRM 前端，r2/Q28） | 接口契约、卡片设计规范、mock 联调 |
| 下游 MCP 服务 | 外部数据属主（服务已有，3 工具随本需求开发） | 数据工具契约、统计口径、PII 脱敏 |

注意：分析对象是**活跃画像客户**（平台客户 ID），不是本系统业务用户；画像不服从 `crt_user` 归属隔离（平台级可见，Q9）。

## 4. 用户故事

1. 作为销售人员，我想在客户画像详情页看到结构化画像卡片（评分/速读/策略/话术），以便快速了解客户并决定下一步
2. 作为销售人员，我想复制 AI 生成的销售话术直接使用，减少话术准备时间
3. 作为销售人员， 我想按评分筛选/排序客户列表（质量/热度/优先级/完整度），以便批量定位跟进对象
4. 作为销售人员，我想手动刷新某个客户的画像（含休眠客户），以便获取最新分析或盘活旧客户
5. 作为系统管理者，我想让活跃客户画像定时批量预生成，以便销售打开详情页时无需等待
6. 作为系统管理者，我想让每次分析记录模型与 token 消耗，以便成本可归因

> 页面由宿主业务系统承载（r2/Q28）：故事 1–4 的界面由宿主方按本模块交付的设计规范实现，本模块保证接口能力。

## 5. 术语

| 术语 | 定义 |
|---|---|
| 活跃画像客户 | 平台画像客户中近 7 天存在消费记录的子集；定时扫描覆盖范围（手动触发不受此限），见 GLOSSARY |
| 销售画像 | 面向销售转化的一次分析产出：三项 AI 评分 + 规则计算的完整度 + 速读/策略/话术；覆盖式只留最新 |
| 销售画像技能 | 配置于百炼 Agent 侧的分析规则/输出结构/取数策略指令资产；本仓库镜像 `sales-skill.md` 为单一事实源 |
| 评分面板 | 画像卡片评分区：`leadQuality`（高/中/低）/ `intentHeat`（热/温/冷）/ `followPriority`（P0~P3）AI 判断 + `infoCompleteness`（0~100%）规则计算 |
| 信息完整度 | 客户资料填写完备程度：基准字段非空加权计算（Q13 规则算法，v1 硬编码清单），恒定可解释 |
| 休眠客户 | 已绑定但近 7 天无消费的客户——不在定时扫描范围，但手动触发允许（Q12） |
| 触发来源 | 两种：SCAN（扫描）/ MANUAL（手动）；无 INIT（活跃集由周期扫描自然覆盖，无存量初始化需求） |

## 6. 与运营画像（ops）的差异速览

| 维度 | ops 运营画像 | sales 销售画像（本模块） |
|---|---|---|
| 分析对象 | 绑定客户全量（GMV 阈值初始化 + 规则扫描） | 绑定 + 近 7 天消费活跃子集（周期扫描） |
| 触发 | SCAN / MANUAL / INIT | SCAN / MANUAL（无 INIT） |
| 评分 | 全 AI 标签（tier/lifecycle/churnRisk） | 三项 AI 评分 + 完整度**规则计算**（Q13） |
| 冷启动 | 降级画像 / 扫描跳过（FR-08） | **无此概念**：数据稀少照常分析 + 速读声明"数据有限"（Q22） |
| 失败语义 | 强校验即弃 | 相同（Q4 对齐） |
| 数据工具 | 统计 MCP 7 工具（另行立项） | 同一 MCP 服务**新增 3 工具**（随本需求开发，Q2/Q17） |
| 前端 | 无（另行安排） | 有，宿主业务系统承载（r2/Q28），本模块交付契约+设计规范 |
| 表 | `ai_customer_profile` | `ai_customer_profile_sales`（不共表，Q8） |
