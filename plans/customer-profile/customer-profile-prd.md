# PRD: 用户画像（customer-profile 模块 · 新用户转化）

> 状态：**v1.0（草案待审）** — 2026-08-26
> 决策记录：Q1–Q28 已于 2026-08-26 四轮 Grilling 确认（Round 3 Q18–Q23、Round 4 Q24–Q28 按推荐执行），详见 [customer-profile-interview.md](customer-profile-interview.md)。
> 本模块取代已废弃的 customer-profile-sales（一期销售转化画像）与 customer-profile-ops（二期运营画像）——两模块文档已标废留痕；同日 roadmap 排期（一期/二期）一并作废。
> 前置母本：`plans/scheduled-task-prd.md`（画像域共同模式来源：DB 行级原子抢占、token 审计纪律、覆盖式 upsert）；`plans/customer-profile-sales-prd.md`（已废弃，卡片七区块线框与画像域质量基线沿用其定版口径，业务方指定新模块沿用该线框）。
> 前置依赖：下游 MCP 数据服务（1 个数据工具，随本需求同步开发）；百炼 Agent（MCP 工具 + skill 配置）；老系统用户检索接口（宿主前端接入）。

## Problem Statement

销售团队面对大量**已注册但尚未消费**的新客户，缺乏系统化的转化认知：不知道谁值得优先跟进、意向处于什么阶段、该用什么样的话术推动他绑定店铺并完成首单。目前完全依赖销售个人经验逐个翻客户资料判断，效率低、标准不统一、跟进时机靠感觉。

**目标**：为每个注册未消费客户生成一张**结构化画像卡片**（评分面板 / 线索速读 / 转化策略 / 可复制话术），帮助销售快速了解客户并决定下一步行动，推动客户**绑定店铺 → 首单支付成功**。

**分析对象（Q2/Q25）**：平台已注册且**无已支付订单**的客户。支付成功即转化成功、即出池；**下单未付仍在池内**（属催单场景）。绑店与否不作入池硬条件——未绑店恰是转化前信号。

**转化定义（Q3/Q25）**：两步目标——绑定店铺 + 开始下单交易；**首单支付成功 = 转化成功**。策略与话术按转化阶段分流：未绑店 → 促绑店；已绑店未首单 → 促首单（Q14）。

## Solution

在 `ehub-ai-workbench` 服务新增独立模块 `customer-profile`（用户画像），前端页面（检索列表 + 画像列表 + 详情卡片）由**宿主业务系统承载，不挂钩 ehub-web**（沿用画像域基线）：

- **数据获取**：下游 MCP 服务新增 1 个数据工具（Q8→Q24 修订）——新用户信息（`customer` + `customer_extend` 两表合并，出参含**消费状态**字段）；池发现权归老系统（复用其用户检索接口），本系统不做客户清单发现（Q16/Q26）
- **AI 分析**：百炼 Agent 非流式调用，按用户画像技能（skill）调用数据工具，输出固定 schema 画像 JSON（三项 AI 评分 + 速读 + 策略 + 话术）；skill 按转化阶段硬分流；**信息完整度由本服务规则计算**（Q15/Q20），不入 AI 输出
- **评分面板**：`leadQuality`（高/中/低）、`intentHeat`（热/温/冷）、`followPriority`（P0~P3）AI 综合判断；`infoCompleteness`（0~100%）规则计算（四层基准，问卷五项约 60% 权重）
- **触发（Q9/Q10/Q11/Q17）**：v1 **纯手动单个触发**——老系统检索列表行内「生成画像」+ 详情页「重新生成」；无定时扫描、无周期重扫、无自动全量回填（自动化全量 → v2）；触发时实时校验池资格（消费状态）与并发占用（行级抢占）
- **失败语义（Q15 沿用）**：固定 schema 强校验失败自动重试 1 次，再失败即弃并记失败状态，**严禁宽松落库**——无 FALLBACK 降级形态
- **存储（Q28）**：表 `ai_customer_profile`（基名直接继承）：`profile_json` 整包（唯一事实源）+ 五投影列（lead_quality / intent_heat / follow_priority / info_completeness + 转化阶段）；覆盖式 upsert 只留最新
- **前端双列表架构（Q26）**：老系统检索列表（找客户 + 触发生成）+ 本服务画像列表（仅已生成画像客户，服务端五筛选：质量/热度/优先级/完整度/转化阶段；默认排序 follow_priority 升序 + generated_at 降序，未生成排最后）

## User Stories

1. 作为销售人员，我想在老系统检索列表中对注册未消费客户一键生成画像，以便快速获得该客户的转化分析
2. 作为销售人员，我想在画像详情页看到结构化画像卡片（评分/速读/策略/话术），以便快速了解客户并决定下一步跟进动作
3. 作为销售人员，我想按转化阶段筛选客户（未绑店 / 已绑店未首单），以便按阶段组织我的跟进工作队列
4. 作为销售人员，我想在画像列表按评分筛选/排序客户（质量/热度/优先级/完整度），以便批量定位高优先级跟进对象
5. 作为销售人员，我想复制 AI 生成的销售话术直接使用，减少话术准备时间
6. 作为销售人员，我想对已生成画像的客户重新生成画像（含数据变化后），以便获取最新分析
7. 作为销售人员，我想在客户已转化后仍能回看其画像卡片，以便复盘"为什么他能转化"
8. 作为系统管理者，我想让每次分析记录模型与 token 消耗（对齐 scheduled-task 既有审计纪律），以便成本可归因

## Implementation Decisions

**总体策略**：对齐画像域已定版基线（前置母本 scheduled-task：行级抢占、token 审计；画像域共同存储形态：`profile_json` 整包 + 投影列、强校验失败即弃、覆盖式 upsert），差异点集中在：分析对象（新用户）、触发（纯手动）、数据面（两表 + 1 工具）、双列表架构、策略按转化阶段分流。

### 对象与池

1. **入池口径（Q2）**：已注册且无已支付订单；不设注册天数窗口、绑店不作硬条件
2. **出池口径（Q25）**：首单**支付成功**即出池；下单未付仍在池内；实现口径（`has_order` 字段 or 支付流水）归数据属主，本 PRD 只锁业务语义
3. **出池处置（Q12）**：画像冻结保留、详情可回看；画像列表默认只显示池内客户；已出池客户不可再触发生成
4. **既有业务字段（Q6）**：`customer_extend.tag`/`level` 等**只读消费**作 AI 输入特征，AI 不回写业务核心表

### 数据与下游

5. **数据边界（Q4）**：v1 仅 `customer` + `customer_extend` 两表；行为日志数据工具 → v2
6. **MCP 工具（Q8→Q24）**：下游最终 1 个工具——新用户信息（两表合并），出参**含消费状态字段**（是否有已支付订单，口径归数据属主）；原「注册未消费清单」工具作废（池发现权归老系统，Q16）；正式契约随 requirements/03 与 MCP 团队定稿
7. **PII 边界（Q15 沿用画像域基线）**：终端消费者 PII 不进 AI 链路；数据工具出入参以平台 ID 与画像所需字段形态提供

### 触发与并发

8. **纯手动触发（Q9/Q10/Q11/Q17）**：老系统检索列表行内「生成画像」（无画像或需重生成均可）+ 画像卡片详情页「重新生成」；仅单个触发，无批量（→v2）；无定时扫描、无周期重扫、无自动全量回填（→v2）
9. **触发时池资格校验（Q24）**：触发请求实时调工具①取消费状态——已出池（已支付）拒绝触发；分析进行中重复触发幂等拒绝（`PARAM_ERROR "分析进行中"`，沿用画像域基线）
10. **并发抢占（Q15 沿用）**：DB 行级原子抢占（复用 scheduled-task 模式），同一客户同一时刻至多一次分析
11. **无冷却期（Q15 沿用）**：v1 不设重复分析冷却（调试期），token 全量记录观测；稳定后 v2 再议

### AI 分析与输出

12. **Agent 宿主（Q15 沿用）**：百炼非流式 `Application.call`；skill 配置于百炼侧，全文镜像本仓库为单一事实源（PR review 维护 + 手动同步百炼，镜像落 `designs/customer-profile/`）
13. **评分分工（Q15/Q20 沿用）**：`infoCompleteness` 规则计算（恒定可解释），其余三项 AI 综合判断——AI 不得计算完整度，完整度不入 skill 输出 schema
14. **输出 schema（Q15 沿用）**：固定枚举强校验——`leadQuality` 高/中/低、`intentHeat` 热/温/冷、`followPriority` P0/P1/P2/P3、`reading` ≤300 字、`strategy` ≤300 字、`script` ≤500 字（v1 单字符串；多条话术展示由宿主切分，数组化 → v2）；skill 硬约束：**禁止虚构客户未表现出的意向信号**、禁止承诺具体价格/收益数字/时效
15. **策略按转化阶段硬分流（Q14）**：阶段判定来自实时数据（绑店状态），不由 AI 猜——未绑店 → 促绑店策略+话术；已绑店未首单 → 促首单策略+话术
16. **冷启动（Q21）**：刚注册、问卷全空客户照常分析，`reading` 中声明"数据有限，结论仅供参考"——不设门槛、不输出降级画像
17. **完整度基准（Q20）**：四层——问卷五项（engaged_time / weekly_ad_budget / order_volume / niche / service_interest，约 60% 权重）/ 联系方式（chat_account 或 reply_to_email 非空）/ 基础档案（first_name / company / country_id 非空）/ 绑店（stores 非空）；具体分值 requirements 阶段定，PRD 锁字段集

### 存储与检索

18. **画像存储（Q28/Q15）**：表 `ai_customer_profile` 基名直接继承；`profile_json` 整包存储（唯一事实源）；覆盖式 upsert 只留最新，历史版本 → v2
19. **检索投影列（Q18）**：五键——`lead_quality`/`intent_heat`/`follow_priority`（三枚举）+ `info_completeness`（数值）+ 转化阶段；画像列表默认排序 `follow_priority` 升序（P0 在前）+ `generated_at` 降序
20. **审计（Q15 沿用）**：记录 `model`、`input_token`、`output_token`；手动触发操作人由通用审计字段 `upd_user`/`upd_name` 承载（异步落库以 UserContext 快照回填），不设专用字段

### 前端与权限

21. **双列表架构（Q16/Q26）**：① 老系统检索列表（复用老系统用户检索接口，前端接入新页面）——找客户 + 行内触发生成；② 本服务画像列表（仅已生成画像客户）——服务端五筛选排序，销售日常工作队列。不采用单列表前端拼装（筛选形同虚设）或 BFF 合流（过度工程）
22. **画像卡片（业务线框 + Q13/Q19/Q27）**：七区块沿用业务给定线框——Header（客户标识 + **转化阶段标签**：未绑店 / 已绑店未首单 + 操作区[重新生成/刷新] + Meta 行含渠道归因）→ 评分面板（AI×3 + 规则×1，含来源小字）→ 基础画像 → 线索速读（AI）→ 转化策略（AI）→ 销售话术（AI，可多条各带复制）→ Footer（生成时间/触发方式/模型）；设计产物落 `designs/customer-profile/`（ia.md + 原型），作为宿主侧交付规范
23. **基础画像字段（Q13/Q19/Q27）**：七字段——DS 经验 / 周广告预算 / 月订单量预期 / 细分市场 / 意向服务 / 最近登录 / 绑定店铺；**无订单数/成交额**（池内客户恒为 0，Q13 明确移除）；渠道归因进 Header Meta
24. **权限（Q15 沿用）**：v1 平台级可见（内部销售全体），不区分角色/线索归属（→v2）
25. **无画像呈现（Q15 沿用）**：详情页无画像时展示"暂无 AI 分析" + 生成入口；有旧画像展示旧画像 + 生成时间；**无 FALLBACK 降级落库形态**

### 边界

26. **数据合规**：终端用户 PII 不进 AI；MCP 数据工具出入参只含平台 ID 与画像所需字段形态

## Testing Decisions

**策略**：测外部行为不测实现细节；核心是 **schema 校验器**（纯逻辑）、**完整度规则计算**（纯逻辑）与**触发语义**（池资格校验 / 幂等 / 并发抢占）。

优先覆盖：

1. **schema 校验器**：枚举越界、必填缺失、字数超限（300/300/500）、markdown 包裹、虚构信号检测（抽检项）——全部拒收
2. **完整度规则计算**：四层基准字段非空加权，边界（全空=0 / 全满=100）断言
3. **触发池资格校验**：已出池（已支付）拒绝；池内通过
4. **幂等与并发**：分析进行中重复触发拒绝；并发同客户至多一次分析（行级抢占）
5. **重试逻辑**：首败→重试成功（落库）；重试再败（弃+记状态）；无第三次
6. **覆盖式 upsert**：同客户二次分析覆盖旧画像，五投影列同步刷新

**验收标准（Q21，5 条）**：

1. 手动触发出画像成功率（含重试）≥95%
2. 人工抽检 50 客户 `leadQuality`/`followPriority` 与资深销售判断一致率 ≥80%
3. 话术抽检零硬承诺（价格/收益数字/时效）
4. 画像列表五筛选键可用（质量/热度/优先级/完整度/转化阶段）
5. token 消耗全量记录（每条画像含 model/input_token/output_token）

## Out of Scope

- 行为日志数据工具与基于行为的意向评分（v2，Q4）
- 定时扫描、周期重扫、自动全量回填、批量触发（v2，Q9/Q10/Q11/Q17）
- 评分漂移约束（观测期后评估，v2）
- 历史版本保留 + 指标快照（v2）
- 话术数组化 `scripts[]`（v2，随契约定稿）
- 已转化客户复盘分析（v2，Q17 衍生）
- 角色/线索归属隔离（v2，Q24）
- skill 正式文本（随 requirements/03 契约定稿后镜像，PR review 维护）
- MCP 服务实现（下游团队交付；本 PRD 定义对上契约：1 数据工具）
- 老系统用户检索接口实现（宿主侧已有能力，本系统仅消费其前端接入）

## Further Notes

**遗留风险**：

1. v1 无行为数据，`intentHeat`（意向热度）证据仅问卷自报 + 渠道归因 + 最近登录——证据薄、评分偏静态（Q13 已确认接受，skill 判定标准弥补；行为日志 v2 补强）
2. 三项评分全 AI 判断——一致性依赖 skill 质量，人工抽检必须覆盖评分一致性（验收 2）
3. 下游 1 工具随本需求同步开发——进度耦合风险，requirements/03 契约定稿需尽早启动
4. 老系统检索接口能力（能否筛"注册未消费"、字段丰富度）待确认——影响检索列表体验，不影响本服务接口契约
5. 前端宿主在业务系统侧——接口联调与上线节奏依赖宿主团队，建议接口契约先定稿并提供 mock
6. 出池判定依赖下游消费状态口径——`has_order` 字段与支付流水的一致性归数据属主，触发校验与列表过滤共用同一口径，避免"可触发但列表不可见"裂缝

**开发顺序建议**：PRD 定稿 → requirements 01–05 拆解 → 契约对齐（requirements/03 与 MCP 团队 + 老系统检索接口字段确认）→ 卡片 ia 设计（`designs/customer-profile/`）→ 开发（接口 mock 先行，宿主侧并行）。
