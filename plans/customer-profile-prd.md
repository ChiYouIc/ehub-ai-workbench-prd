# PRD: 客户画像 AI 分析 v1（customer-profile 模块）

> 状态：**v1.3（已定版）** — 2026-08-25
> 决策记录：Q1–Q27 已于 2026-08-25 四轮 Grilling 确认；r2 修订（Q28–Q35）：数据获取改为原子化数据工具 + 画像技能编排；r3 修订（Q36–Q38）：GMV 分位数 v1 不可用，valueTier 改绝对值档位表、初始化改绝对阈值筛选；**r4 修订（Q39）：画像存储改整包 `profile_json` + 检索投影列（指标新增/变更零 DDL）**。详见 `plans/customer-profile-interview.md`。
> 前置依赖：独立下游 MCP 统计服务（外部依赖，另行立项）；百炼 Agent（MCP 工具 + skill 配置）。
> 前置母本：`plans/scheduled-task-prd.md`（调度模式来源：@Scheduled 轮询 + DB 行级原子抢占）。

## Problem Statement

平台拥有 1 万~10 万绑定店铺的 B2B 代发客户（月单量几百~上千不等），但运营对客户缺乏系统化认知：不知道谁高价值、谁在流失、谁在快速增长。客户分层与差异化服务（重点经营高价值客户、提前干预流失风险）目前完全靠人工经验，覆盖不了这个量级。

目标（Q1）：**提升用户转化、降低流失风险**。

数据现实约束（Q2/Q4）：具备客户基础信息、绑定店铺、订单、商品品类、采购、物流、售后、资金八类数据；但量级决定了**原始订单不可能直接进 AI**——必须是"统计预计算 → AI 解读"两段式。

## Solution

在 `ehub-ai-workbench` 服务中新增**独立模块 `customer-profile`**，构建自动化客户画像流水线：

- **原子化数据获取（Q28，r2 修订）**：独立下游 MCP 统计服务提供约 7~8 个**按业务问题切分的数据工具**（客户基础信息/订单规模与趋势/品类分布/履约售后/资金状况/平台基线/规则筛选客户列表），带时间窗口参数，回溯上限 365 天（Q34）
- **画像技能编排（Q29/Q33）**：百炼 Agent 侧配置画像技能（profiling skill）——规定固定必调序列（取数策略）、分析规则、输出结构；skill 全文以本仓库镜像为单一事实源，PR review 后手动同步百炼
- **AI 分析**：非流式调用，Agent 按技能依次调用数据工具拼装指标包，输出**固定 schema 画像 JSON**（分层/生命周期/流失风险/品类/特征/建议动作）+ ≤200 字中文经营摘要
- **双触发**：本服务定时任务按 5 条内置规则周期扫描预筛命中客户（非全量）；运营后台手动触发指定客户（冷启动客户降级画像）
- **三层失败语义（Q32）**：工具层失败结构化返回 Agent，按技能指引重试 1 次或跳过并声明缺失；整体异常走服务层校验失败重试 1 次，再失败即弃
- **强校验落库**：画像覆盖式存本服务新表，平台级可见
- **存量初始化（r3 修订）**：按绝对 GMV 阈值筛选先行客户（近 90 天 GMV ≥ skill 档位表 T2 下限）；v2 分位数能力上线后切回"前 20%"相对口径

## User Stories

1. 作为运营人员，我想查看指定客户的 AI 画像（价值分层、生命周期、流失风险、主营品类、经营特征、摘要），以便快速了解一个不熟悉的客户
2. 作为运营人员，我想按条件筛选客户列表（如 churnRisk=HIGH、valueTier=T1、lifecycle=DECLINING），以便批量定位需要干预的客户群体
3. 作为运营人员，我想让系统自动发现异常客户（GMV 大幅下滑、连续衰减、售后超标、疑似流失、快速增长），无需人工盯盘
4. 作为运营人员，我想在客户详情页手动触发"立即分析"，以便现场获取或刷新某个客户的画像
5. 作为运营人员，我想让冷启动客户（数据不足）得到降级画像而非误导性结论，以便正确看待新客户
6. 作为运营人员，我想让画像对全体内部用户可见（平台级共享），以便跨运营协作使用同一份客户认知
7. 作为系统管理者，我想让每次分析记录所用模型与 token 消耗，以便成本可归因、可观测

## Implementation Decisions

**总体策略**：规则算硬指标、AI 做软判断（Q7）；固定 schema 强校验（Q8）；本服务为薄编排层（取指标 → 组装触发 → 调百炼 → 校验落库）。

### 架构与模块

1. **模块归属（Q20）**：新独立模块 `customer-profile`，不与 scheduled-task 共表（语义完全不同）；复用其已验证的**模式**——`@Scheduled` 固定延迟轮询 + DB 行级原子抢占（多实例安全，见 architecture §4）
2. **两段式数据架构（Q4 结论/Q6/Q13，r2 修订 Q28）**：统计口径归下游 MCP 统计服务（数据属主）；工具粒度为**按业务问题切分的原子化数据工具**（约 7~8 个，带时间窗口参数，上限 365 天）——既服务画像的固定序列取数，也为 v2 对话式分析的按需取数铺路（Q30）；指标包降级为逻辑概念（多工具结果拼装）
3. **Agent 宿主（Q14）**：继续百炼，非流式 `Application.call`；数据工具经 MCP 接入，画像技能配置于百炼 Agent 侧
4. **画像技能内容与版本管理（Q29/Q33）**：技能规定——固定必调序列（工具 1→…→6，工具 7 供扫描路径）、valueTier 判定标准、输出 schema、失败指引（单工具连续失败 2 次跳过并在 summary 声明数据缺失）；skill 全文镜像于本仓库（`designs/customer-profile/profiling-skill.md`）为**单一事实源**，变更走 PR review，手动同步百炼
5. **轮次护栏（Q31）**：百炼不暴露工具轮次计数，服务层不做硬限；超时兜底对齐 scheduled-task 120s 模式；轮次约束写入 skill（软约束，Agent 是否遵守不做强要求），token 记录观测实际消耗
6. **工具失败语义（Q32）**：三层分工——工具层结构化错误返回 Agent（可补救跳过）；Agent 层整体异常；服务层只管最终 schema 校验（沿用 Q23 重试 1 次策略）

### 触发与扫描

7. **触发机制（Q15）**：本服务定时任务周期扫描 + 页面手动触发，不依赖主平台事件通知、不引入 MQ
8. **扫描数据来源（Q15/Q28，开放问题 1 已解决）**：扫描路径调用数据工具 7（规则筛选客户列表）获取命中客户，不对全量客户逐个拉取指标；指标明细仅对命中客户按画像技能序列拉取
9. **扫描规则（Q17，v1 硬编码不做配置化）**：① GMV 环比下滑≥30% ② 订单量连续 3 周环比衰减 ③ 退款/纠纷率超平台基线 2 倍 ④ 历史活跃（月均 50+ 单）近 30 天 0 订单 ⑤ GMV 环比增长≥50%
10. **平台基线来源（开放问题 2 已解决）**：由数据工具 6（平台基线）提供，随数据刷新；规则 ③ 的阈值判断输入来自该工具
11. **冷启动规避（Q12）**：扫描自动跳过数据不足客户；手动触发输出降级画像（仅 NEW 标签 + 基础摘要，无趋势结论）
12. **存量初始化（Q16，r3 修订 Q36）**：v1 按绝对 GMV 阈值筛选先行客户（近 90 天 GMV ≥ skill 档位表 T2 下限，经数据工具 7 绝对阈值筛选取清单）；v2 MCP 分位数能力上线后切回相对分层（前 20%）；长尾等事件自然触发补齐
13. **无冷却期（Q24）**：v1 不设重复分析冷却——上线初期需频繁修改 prompt/skill 调试优化；稳定后 v2 引入

### 输出与存储

14. **AI 输出 schema（Q19，固定枚举强校验）**：`valueTier`（AI 经 skill 决策，Q22 修订；**r3/Q37：v1 判定输入为绝对值档位表**——skill 写死窗口化 GMV 档位，AI 综合 GMV/订单量/客单价在档位边界附近浮动判定；`gmvPercentile` 可得时优先采用）、`lifecycle`（NEW/GROWING/MATURE/DECLINING/DORMANT）、`churnRisk{level, signals[]}`（signals 必须引用指标证据）、`topCategories[]`、`traits[]`（8 枚举多选：品类集中/多品类分散/低价高频/高客单/快速增长/收缩中/季节性/品质敏感）、`suggestedAction`（介入/激励/观察/无，固定枚举禁止自由文本）、`summary`（≤200 字中文）
15. **校验与重试（Q23）**：固定 schema 强校验；失败自动重试 1 次（重试附错误提示），再失败即弃并记失败状态——**严禁宽松落库**
16. **画像存储（Q10/Q21）**：本服务新表；v1 覆盖式只留最新，v2 全量保留 + 指标快照
17. **审计与成本（Q26）**：画像表记录 `model`、`input_token`、`output_token`（对齐 `ai_conversation_content` 既有纪律）；手动触发记录操作人（Q25）

### 边界

18. **数据合规（Q5）**：订单/经营数据可用；终端用户 PII 不进 AI，一律以平台 id 展示
19. **权限（Q25）**：画像平台级可见（不受 `crt_user` 隔离，对齐"平台数据"定位）
20. **预警出口（Q11）**：v1 被动查询，不做主动推送（先验证准确率，避免误报消耗信任）
21. **历史回溯上限（Q34）**：所有数据工具时间窗口参数上限 365 天（契约级约束）；注册天数/绑定天数等存量事实不受窗口限制
22. **GMV 分位数契约留位（Q38，r3）**：数据工具 1 的 `gmvPercentile` 为**可选字段**（v1 缺失，MCP 计划 v2 提供）；skill 写"优先分位数、缺失走绝对档位"——下游上线该指标时两侧零契约变更
23. **画像存储形态（Q39，r4）**：AI 分析输出**整包存 `profile_json`**（原生 json，唯一事实源），仅 FR-06 五个筛选键设检索投影列（写时提取）；新增伴生列 `skill_version`（应用配置注入，schema 演进可追溯）——指标新增/变更**零 DDL**，新指标需检索时再加投影列+回填，不预置

## Testing Decisions

**策略**：测外部行为不测实现细节；核心是**规则引擎边界**与**schema 校验器**两个纯逻辑单元。

优先覆盖：
1. **5 条扫描规则**：阈值边界（恰好 30%、50%）、连续周衰减计数、基线倍数比较、活跃历史的判定窗口
2. **schema 校验器**：枚举越界、必填缺失、markdown 代码块包裹、summary 超长、traits 非法值——全部拒收
3. **重试逻辑**：首次失败 → 重试成功（落库）；重试再失败（弃 + 状态记录）；无第三次调用
4. **工具失败降级路径**：某数据工具结构化错误 → Agent 跳过该数据块继续，summary 声明"履约数据缺失"；连续失败 2 次跳过（skill 指引的行为验证）
5. **降级画像路径**：冷启动客户手动触发 → 输出仅含 NEW + 基础摘要、无趋势字段
6. **行级抢占**：多实例并发扫描同一客户至多一次分析（复用 scheduled-task 既有测试模式）
7. **初始化任务**：GMV 前 20% 覆盖完整性、失败重跑

**验收标准（Q27，5 条；第 1 条 r3 改写）**：近 90 天 GMV ≥ T2 档位下限的客户 100% 有画像（v1 绝对口径，v2 切回前 20%）；人工抽检 50 客户 lifecycle/churnRisk 与资深运营一致率 ≥80%；校验最终失败率 <5%；token 成本有记录；冷启动降级正确。

## Out of Scope

- **MCP 统计服务本身**（独立下游服务，另行立项；本 PRD 定义其对上契约：7~8 个数据工具清单与时间窗口约束）
- **画像技能正式文本**（随 requirements/03 契约定稿后，在本仓库镜像 `designs/customer-profile/profiling-skill.md`，PR review 维护）
- 画像历史版本保留 + 指标快照（v2，Q21）
- 重复分析冷却期（v2，Q24）
- 高风险客户主动推送（v2，Q11）
- 扫描阈值配置化（Q17：稳定运行 3 个月后再议）
- 评分制、可视化看板（Q3 仅标签+摘要）
- **对话式分析入口**（v2 明确规划，Q30：数据工具按业务问题切分正是为其铺路；v1 不进验收标准）
- 前端 UI（本 PRD 仅后端接口，对齐 scheduled-task 惯例）

## Further Notes

**遗留风险**（继承 grilling 记录）：

1. valueTier 由 AI 判断（Q22 修订），分层一致性完全依赖 skill 质量——人工抽检必须覆盖分层一致性
2. 无冷却期 → 调试期 token 成本波动大，靠成本记录观测
3. 覆盖式存储 → 无法复盘 AI 历史判断，prompt 迭代对比依赖人工抽检
4. 多轮工具调用 → 单次画像成本/延迟高于单工具方案，且轮次仅 skill 软约束（百炼不暴露轮次计数，Q31）——超时兜底 + token 观测
5. 串行调用失败率乘法效应（每工具 99% 可用 → 7 工具链 ≈93%）——靠工具层结构化错误 + Agent 跳过降级对冲（Q32）
6. 绝对档位漂移（r3）：平台增长/季节波动使 T1~T5 边界失真——档位表随 skill 版本化管理、定期 review；v2 分位数切回相对分层（Q36/Q37）
