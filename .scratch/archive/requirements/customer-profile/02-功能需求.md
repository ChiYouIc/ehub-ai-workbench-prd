# 02 功能需求 — 用户画像模块（新用户转化）

> 模块：customer-profile ｜ 关联 PRD 母本：[`plans/customer-profile/customer-profile-prd.md`](../../plans/customer-profile/customer-profile-prd.md)（v1.3 草案待审） ｜ 状态：**前置拆解稿**（PRD 终审定稿时复核）
>
> 编号规则：`FR-xx`，模块内递增不复用。验收标准描述**外部可观察行为**。错误码复用既有 `ErrorCodeEnum`（PARAM_ERROR / NOT_FOUND），不新增（新增需先走 [`../web/02-错误与异常.md`](../web/02-错误与异常.md) 演进流程）。
>
> 覆盖 PRD 决策：8（纯手动触发）/ 9（触发池资格校验）/ 10（并发抢占）/ 11（无冷却期）/ 13（评分分工）/ 14（输出 schema）/ 15（策略按阶段硬分流）/ 17（完整度基准）/ 18（覆盖式 upsert）/ 19（检索投影列）/ 20（审计）/ 22（画像卡片）/ 25（无画像呈现）。

## FR-01 触发生成画像

**需求**：销售人员对注册未消费客户一键生成画像（宿主检索列表行内「生成画像」触发）。

**验收标准**：
1. 请求体 `{customerId}`；`customerId` 非空白 → 否则 `PARAM_ERROR`
2. 触发请求**实时**调 `customer detail` 取「是否有已支付订单」：=是（已出池）→ 拒绝触发 `PARAM_ERROR "客户已转化，不在画像范围"`（Q24）
3. 该客户 `run_state=RUNNING`（分析进行中）→ 幂等拒绝 `PARAM_ERROR "分析进行中"`（Q9，沿用画像域基线）
4. 抢占成功 → 返回成功（**异步受理**，不等分析结果；前端凭详情 `runState` + 卡片「刷新」观察进度，见 ※D-1）
5. 分析完成 → 固定 schema 强校验（枚举/字数/条数/阶段一致/虚构信号抽检）失败自动重试 1 次；重试再失败 → 弃 + 记失败状态（`run_state` 复位 IDLE + 失败标记），**严禁宽松落库**、无 FALLBACK 降级形态（Q15）
6. 无冷却期：v1 不设重复分析冷却（Q11，token 全量记录观测）

## FR-02 画像详情

**需求**：销售人员查看单个客户的结构化画像卡片。

**验收标准**：
1. 返回画像详情：`profileJson` 整包 + 五投影列 + `stage` + `runState` + `updTime`（承载画像最近时间，供详情展示）+ `runError` + 审计（`model` / `inputToken` / `outputToken`）+ `outOfPool`
2. **无画像** → 返回空态（`profile=null`，非错误），前端展示"暂无 AI 分析"+ 生成入口（Q25）
3. **有旧画像** → 返回旧画像 + `updTime`（Q25）
4. 已出池客户**仍可回看**（详情访问不拒绝；回看不触发重新校验）；已出池不可再触发生成（Q12/FR-04）
5. 详情路径发现已出池 → 惰性回写 `out_of_pool=1`（※D-6）

## FR-03 画像列表（服务端五筛选）

**需求**：销售人员按评分/阶段筛选排序已生成画像客户（本服务画像列表 = 销售日常工作队列）。

**验收标准**：
1. 服务端**五筛选键**：`leadQuality`（高/中/低）、`intentHeat`（热/温/冷）、`followPriority`（P0~P3）、`infoCompleteness`（区间 Min/Max）、`stage`（未绑店/已绑店未首单）（Q18/Q26）
2. 默认排序：`followPriority` 升序（P0 在前）+ `updTime` 降序（最近画像写入在前；时间由通用审计 `upd_time` 承载，Q19）
3. 默认只显示**池内客户**（`out_of_pool=0`，Q12）；已出池客户不出现在列表（回看走详情）
4. 分页 `page`/`size`（边界同会话组列表：`page<1` 默认 1，`size>50` 截断 50）；空列表返回 `total=0, data=[]`
5. 筛选枚举非法值 → `PARAM_ERROR`；`infoCompletenessMin > Max` → `PARAM_ERROR`

## FR-04 重新生成画像

**需求**：销售人员对已生成画像客户重新生成（详情页「重新生成」）。

**验收标准**：
1. 池资格校验同 FR-01 验收 2（已出池 → `PARAM_ERROR`，拒绝重新生成）（Q12）
2. 幂等同 FR-01 验收 3（分析进行中 → `PARAM_ERROR "分析进行中"`）
3. 重新生成成功 → **覆盖式 upsert**：`profile_json` 整包 + 五投影列整体覆盖旧画像，只留最新（Q28/FR-06）
4. 重新生成失败（重试后再败）→ **旧画像保留**，不因新分析失败而丢旧画像（Q25）

## FR-05 完整度规则计算（infoCompleteness）

**需求**：`infoCompleteness`（0–100）由**本服务规则计算**（非 AI 输出），输入为 `customer detail` 文案形态出参。

**验收标准**（纯逻辑，单测覆盖）：
1. 五层基准按 ※D-3 分值加权：问卷五项各 12（合计 60）/ 联系方式 10 / 基础档案 10（姓名 4 + company 3 + country 3）/ 渠道归因 10 / 绑店 10
2. 解析口径（※D-4）：**只识别空值标记（普通 `-` / 渠道 `--`）与布尔形态**——问卷五项/基础档案层按非空即记已填、联系方式/姓名层按布尔信号、渠道归因层按渠道来源是否 `--`、绑店层按 `stores` 是否为空；**不解析枚举文案语义**
3. 边界断言：全空 = 0 / 全满 = 100
4. 结果四舍五入取整；`profile_json` 不落完整度（完整度由本服务计算投影列，Q20）

## FR-06 覆盖式 upsert（存储）

**需求**：画像存储只留最新版本（`profile_json` 整包为唯一事实源）。

**验收标准**：
1. `customer_id` 唯一（唯一键）；同客户分析成功 → ON DUPLICATE KEY UPDATE 覆盖整包 + 五投影列 + 审计字段
2. 历史版本不保留（→v2，Q28）
3. `run_state` 控制面与画像数据面分离：抢占用 `run_state` 原子 UPDATE，结局不依赖 `run_state` 存续（对齐 scheduled-task 两字段分离理由）

## FR-07 审计记录

**需求**：每次分析记录模型与 token 消耗（对齐 scheduled-task 既有审计纪律）。

**验收标准**：
1. 每次成功落库含 `model` / `inputToken` / `outputToken`
2. 手动触发操作人由通用审计字段 `upd_user`/`upd_name` 承载（异步落库以 UserContext 快照回填），不设专用字段（Q15/决策 20）
