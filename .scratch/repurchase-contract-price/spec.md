# 1688 复购合约价接入（repurchase-contract-price）

Status: ready-for-agent

溯源：TAPD 需求 [1136062570001009339【功能完善】1688复购合约查询，和协议价相关](https://www.tapd.cn/36062570/prong/stories/view/1136062570001009339)（无本地 PRD，本 spec 为该需求的唯一规格母本）。实现工单见 `issues/`。

## Problem Statement

1688 已开放复购合约价 API（`com.alibaba.trade:repurchase.contract.get-1`）：买卖家对常购商品约定专属价格的合约协议，支持约定有效期内的阶梯量价、运费、开票、发货交期，**买家下单无须改价**。

而本系统当前的协议价体系是「人工双轨」：销售录一份、供应商录一份，存于 1688 商品货源信息（third_ali_product_info）中，仅作为展示与付款校验参考。实际下单仍走普通 flow，需要供应商人工改价后采购员才能付款，导致：

1. 采购员看不到权威的合约阶梯价，需手动对照 1688 合约换算档位价；
2. 命中合约的商品因走 general flow 下单，无法享受合约价，仍要等供应商改价；
3. 人工协议价可能与 1688 实际合约价偏差，无人发现；
4. 合约到期/终止、数量不达档、收货地址超出包邮区三类失效场景无兜底，按错误预期下单会落空。

## Solution

接入 1688 复购合约 API，把合约价建立为权威价格数据源，与现有人工协议价（AP）双轨并存、对账互补：

1. **SDK 升级 + 合约查询服务**：升级 1688 开放平台 SDK，新建「复购合约查询服务」，按（1688 商品 + 规格 + 数量 + 收货地址）返回生效合约报价（命中档位价、运费、包邮性、有效期等）；
2. **价格展示接入**：待下单/待付款等价格展示节点按采购数量自动匹配阶梯档位，展示合约价（独立标签，与 AP 标签区分）；
3. **下单 flow 改造**：新增 `repurchase` 交易 flow；命中合约价的订单自动/强制走该 flow 提交，买家下单无须改价；
4. **三类失效兜底**：数量不达档、收货地址超出合约包邮地区、合约到期或被单方终止时，下单前实时校验并给出明确提示或回退；
5. **配套管理能力**：合约自动同步、人工协议价版本留痕、协议价与合约价对账预警、合约临期提醒、合约异常报表（漏合约/价不一致）。

## User Stories

**合约数据源与同步**

1. 作为采购员，我希望系统自动从 1688 拉取商品规格级的生效复购合约，以便不用去 1688 后台人工查合约价。
2. 作为系统，我需要在下单预览时同步合约的新建、续签、变更，并定时巡检到期、终止状态，以便本地合约数据与 1688 保持一致。
3. 作为采购主管，我希望合约同步任务失败时有告警，以便及时发现并修复同步异常。
4. 作为采购员，我希望下单前的合约校验以 1688 实时接口结果为准，以便本地缓存过期也不会按失效合约下单。

**价格展示**

5. 作为采购员，在待下单清单看到某 SKU 命中复购合约时，我希望系统按当前采购数量自动匹配阶梯档位并展示合约单价，以便不用手动对照阶梯表换算。
6. 作为采购员，我希望合约价与人工录入协议价（AP）用可区分的标签展示，以便一眼识别价格来源。
7. 作为采购员，当采购数量未达到合约最低档时，我希望看到差额数量提示，以便决定补量还是按普通价下单。
8. 作为采购员，我希望看到合约约定包邮地区与当前收货仓库地址是否匹配的提示，以便预判是否产生额外运费。
9. 作为采购员，我希望看到合约的剩余有效期，以便判断合约即将到期时是否值得凑量下单。
10. 作为销售，我希望在协议价管理页看到 1688 合约价与我录入的协议价并排对比，以便发现录入偏差并及时修正。

**下单 flow**

11. 作为采购员，当待下单商品命中合约价时，我希望系统自动把该供应商组的下单 flow 切换为复购合约（repurchase），以便订单真正享受合约价。
12. 作为采购员，如果我手动把命中合约的商品切换为普通 flow，我希望提交时被阻断并提示，以便不会误下单损失合约价。
13. 作为系统，提交订单到 1688 前我需要实时复查合约有效性，以便合约恰好失效时立即回退或终止提交。
14. 作为采购员，命中合约的订单提交后，我希望无须等待供应商改价即可进入付款环节，以便缩短采购周期。

**失效兜底**

15. 作为采购员，当采购数量不达合约档位时，我希望下单前收到明确提示（补量差额或改走普通价），以便避免按合约预期下单后落空。
16. 作为采购员，当收货地址超出合约包邮地区时，我希望收到运费提示后再确认下单，以便知情决策。
17. 作为采购员，当合约到期或被单方终止时，我希望系统回退为普通价展示与普通 flow 下单，以便采购流程不中断。

**对账与预警**

18. 作为采购主管，我希望人工协议价与 1688 合约价偏差超过阈值时自动产生预警，以便推动销售及时修正录入。
19. 作为销售，我希望协议价的每次修改都保留历史版本（谁、何时、改成什么），以便追溯价格变化责任。
20. 作为采购主管，我希望看到「有人工协议价但 1688 无生效合约」与「有合约但无人工协议价」两类异常清单，以便清理双轨数据的脏数据。

**提醒与报表**

21. 作为销售，我希望合约临期（可配置天数）时收到系统提醒，以便与供应商续签或重新谈价。
22. 作为采购主管，我希望有合约异常报表（漏合约、价不一致、临期未续），以便周期性巡检合约价体系的健康度。

**付款环节**

23. 作为采购员，待付款列表中合约价订单我希望按合约价金额直接校验毛利率并付款，以便付款规则与真实成交价一致。
24. 作为财务，我希望合约价订单的协议价金额字段反映 1688 实际合约价，以便成本核算不失真。

## Implementation Decisions

> 涉及两仓库：后端 ehub（Java，1688 SDK/服务/存储）、前端 ehub-web（Vue2 + Element-UI）。以下按模块描述，不含具体文件路径。

### 术语澄清（重要，避免撞名）

- 系统内已有「合约采购」（线下合约，contractUrl/contractAmount 那条线）与「重采」（repurchaseStatus、repurchase 列表）两个概念。本特性的「**复购合约**」是 1688 平台侧的第三种概念，UI 文案统一用「复购合约」，不得简写为「合约」或「重采」。
- 交易 flow 标识符沿用 1688 官方名 `repurchase`（与 general / saleproxy / startingBulk 并列），尽管与「重采」英文撞名，对齐 1688 文档优先。

### 后端（ehub）

1. **SDK 升级**：升级 1688 开放平台 SDK 至支持 `repurchase.contract.get-1` 的版本；1688 网关 client 接口新增「查询单个商品规格生效合约」方法，返回合约 ID、阶梯量价档位、运费/包邮地区、开票方式、发货交期、有效期、状态。
2. **复购合约查询服务（新模块）**：
   - 查询契约：输入（1688 offerId、specId、采购数量、收货地址编码），输出合约报价对象：是否命中、合约 ID、命中档位（档位序号/起批量/单价/运费）、是否包邮（地址维度）、开票方式、交期、有效期起止、合约状态。
   - 档位匹配规则：采购数量落入「满足起批量的最高档」即该档单价；数量低于最低档视为不达档。
   - 同步策略：**下单预览触发同步**（详见下「下单预览触发的合约同步流程」）；本地合约快照 + 下单/提交前的实时复查（实时结果覆盖快照），保证失效兜底的强一致；定时任务不承担全量同步，仅做生命周期巡检（到期/终止打失效标记）。

   **下单预览触发的合约同步流程**（tenant 后端视角）：

   1. 前端请求下单预览 → tenant 组装本次预览涉及的 1688 offerId 集合（按供应商组去重）；
   2. 逐个查本地 price_info 中的 repurchase 元素：`updTime` 在 TTL 内（默认 5 分钟，可配置）→ 直接用快照，跳过远程调用（TTL 判断为后续工单，当前实现每次预览均触发同步，靠幂等写库兜底）；
   3. 未命中/过期的 offerId 批量调用 alipur 合约查询接口（`POST /restful/ali/trade/repurchase/contract`）；
   4. 远程结果落库（**不建新表、不加新列**，全部落在 `third_ali_product_info.price_info` 内，与人工协议价元素同数组共存）：
      - 行级存储单元：一个带 `repurchase:true` 标识的 JSON 数组元素，内容为该行 specId 对应 sku 的阶梯价（`RepurchasePriceRange` 数组原样转 JSON，`price` 单位分）+ `updTime`（同步时间，yyyy-MM-dd HH:mm:ss）+ `expired`（过期标记，正常同步恒为 false）；
      - 有合约 → 把上述元素合并进 price_info（已有 repurchase 元素则原位替换，人工协议价元素原样保留）；
      - 无合约（含 sku 不在合约列表）→ 不删除元素，把现存 repurchase 元素内 `expired` 置 true 标记失效（保留 skuId 与阶梯价快照供追溯，人工协议价不动；已是失效状态则不写库幂等）；「无合约」负缓存（带 TTL）暂不实现，后续工单再定；
      - 幂等：合约阶梯价内容无变化时不写库、不刷新 updTime；price_info 解析失败（脏数据）时放弃该行合并，保留现状；
      - 调用失败 → 降级：记录告警日志、跳过同步，不阻断预览主流程；
   5. 继续原有 1688 下单预览（createOrderPreview），预览响应附加合约报价摘要（命中与否、命中档位价、失效原因码），前端据此展示合约价标签。
3. **合约快照存储（price_info 字段内合并，不建新表/新列）**：合约快照以行级 sku 阶梯价元素形式合并进 `third_ali_product_info.price_info`（元素结构见决策 2 第 4 条），人工协议价元素与 repurchase 元素在同一数组共存；失效一律不删除元素（预览同步发现无合约、定时巡检发现合约到期/终止，均把元素内 `expired` 置 true，保留 skuId 与阶梯价快照供追溯；合约恢复时同步原位替换并翻回 `expired=false`）；合约的运费/包邮地区/开票/交期等 offer 级条款不落地存储，下单前实时向 1688 复查。
4. **订单创建服务改造**：交易 flow 枚举增加 `repurchase`；提交前规则——
   - 命中合约 → 必须以 repurchase flow 提交（普通 flow + 命中合约 = 拒绝并返回结构化错误）；
   - repurchase flow → 实时复查合约，三类失效返回带错误类型的结构化错误：`QUANTITY_BELOW_TIER` / `ADDRESS_NOT_COVERED` / `CONTRACT_INVALID`，由前端转译为人话提示；
   - 失效兜底允许人工选择回退普通 flow 重提。
5. **对账预警任务**：定时比对合约快照价与人工协议价（third_ali_product_info.price_info，按元素类型区分：repurchase 元素即合约价，普通元素即人工录入值），偏差超过可配置阈值（百分比）生成预警记录并通知；同时产出两类异常清单（人工录入值与合约快照价不一致 / 有合约价但从未有人工录入）。
6. **协议价版本留痕**：协议价（含阶梯 priceInfoList）每次变更——无论人工编辑还是合约同步覆盖——写一条历史版本（操作人/触发来源、时间、变更前后快照），协议价管理页可查。
7. **有效期提醒**：合约临期（可配置天数，默认 7 天）生成系统提醒给相关销售/采购。
8. **报表接口**：合约异常报表查询（异常类型、商品、供应商、价差、临期天数等维度）。

### 前端（ehub-web）

9. **待下单清单**：命中合约的 SKU 在单价区新增合约价标签（与现有 AP 标签视觉区分），tooltip 展示命中档位与有效期；数量不达档/地址不包邮以警示文案展示；供应商组 flow 单选组新增「复购合约订单」选项，命中合约时默认/自动选中；提交失败的三类结构化错误转译为补量/运费/失效提示。
9a. **合约信息标记（数据源为 price_info 快照）**：待下单清单（`showType=1&status=2` 路径）每个 SKU 行解析后端透传的 `priceInfo`（人工协议价元素 + repurchase 元素同数组共存）：存在 `repurchase:true` 且 `expired !== true` 的元素 → 在 AP 标签旁展示合约标签（样式与 AP 一致）；存在 `repurchase:true` 且 `expired === true` 的元素 → 展示红色（danger）「合约过期」标签；无 repurchase 元素 → 不展示。价格展示与档位匹配（第 9 条）后续工单实现，本条仅做存在性标记。
9b. **采购订单列表合约信息标记**：默认订单列表（tabPane）复用同一标记语义，但解析在后端：`ehub-common` 新增 `RepurchasePriceInfoUtils`（静态工具，只吃 `price_info` JSON 文本，提供 `parse`/`hasActive`/`hasExpired`/`matchTierPrice`，其它模块可复用），`OrderQueryServiceImpl#buildContractPrice` 补查 `priceInfo` 列并在 `TenantOrdersGoodsVo` 上填充 `hasRepurchase` / `repurchaseExpired` 布尔字段，前端照 AP tag 样式展示（有效 primary / 过期 danger）。
9c. **协议价管理页（showType=4）合约只读展示**：`price_info` 的 repurchase 元素**只读、不可编辑**——列表解析时从 `priceInfoList` 剥离（剥离后仅人工协议价元素可编辑），合约以独立只读列展示（tag：生效中 primary / 已失效 danger，tooltip 展示阶梯价与同步时间）。编辑/批量保存提交的 `priceInfoList` 天然不含合约元素；若保存导致合约元素被覆盖，由下单预览触发的同步任务自愈（重新拉取合约原位写回）。不做后端写入侧保底合并。
10. **待付款列表与交易付款弹窗**：合约价订单展示合约价金额（复用现有 contractPriceAmount 展示位逻辑，数据源换为合约报价），付款校验（毛利率 SLA）以合约价为准。
11. **协议价管理页（1688 商品货源 tab）**：新增合约价对比列（合约档位价 vs 人工价，偏差超阈值红色标记），查看版本历史入口。
12. **报表与提醒入口**：合约异常报表页面；临期/对账预警走系统消息通知。
13. **智能选择/加入购物车链路**：现有按 statusValue 多数派推导 flow 的逻辑需纳入 repurchase 类型，避免智能组单把命中合约的组推成 general。

### API 契约（前端 ↔ 后端）

14. 采购清单/待付款列表响应扩展合约报价摘要字段（命中与否、档位价、失效原因码）。
15. 新增接口：合约价对比查询（按商品/供应商维度）、协议价版本历史查询、合约异常报表查询。
16. 下单提交接口的失败响应扩展错误类型字段（见第 4 条三类错误码）。

## Testing Decisions

**好测试的标准**：只测服务边界的外部行为——给定合约数据/数量/地址输入，断言输出的档位匹配结果、flow 决策、错误码与兜底动作；不 mock 被测服务内部协作对象的行为细节，不测私有方法。

**两个测试 seam（已与提出方确认拆分）：**

1. **Seam A：复购合约查询服务**（mock 1688 SDK 网关 client）
   - 档位匹配边界：恰好达档 / 差一件不达档 / 数量跨多档取最高满足档 / 无合约
   - 地址覆盖判断：包邮区内 / 区外 / 合约未约定包邮地区
   - 有效期与状态：未生效 / 生效中 / 到期 / 已终止
   - 同步触发：预览同步的幂等（合约内容无变化不写库、不刷新 updTime）、无合约移除 repurchase 元素且人工协议价元素保留、price_info 脏数据降级保留现状、同步失败不阻断预览；快照命中、实时复查覆盖快照
   - 对账任务：偏差阈值边界（恰好等于阈值不预警 / 超出预警）
2. **Seam B：1688 订单创建服务**（mock 合约查询服务 + 1688 下单 client）
   - flow 决策：命中合约强制 repurchase；普通 flow + 命中合约被拒绝
   - 三类失效兜底：三种错误码的正确返回与透传
   - 回退路径：失效后允许改普通 flow 重提
   - 现有回归：general / saleproxy / startingBulk flow 不受影响

**先例**：后端采购域已有纯 Mockito 单元测试先例（同步服务类 mock 依赖直测），新测试沿用该风格；JDK 1.8 + JUnit4 + Mockito 技术栈。

**前端**：仓库无自动化测试基建（无测试框架与脚本），前端改动以人工验收清单覆盖（展示标签、flow 切换、错误提示转译、报表页面）。

## Out of Scope

- 复购合约的签订、续签、终止操作（在 1688 平台完成，本系统只读）；
- 线下「合约采购」（contractUrl/contractAmount 域）与「重采」流程的任何改造；
- 淘宝/天猫/京东渠道商品（repurchase flow 仅适用于 1688 大市场）；
- 存量历史订单的合约价回溯重算；
